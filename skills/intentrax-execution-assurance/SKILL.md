# Intentrax execution assurance for agent-built applications

Intentrax answers a question ordinary logging cannot: **"what did this agent
intend, what was decided, and can a third party who trusts neither side check
the record?"** It produces a signed, portable proof record that can be verified
offline against pinned public keys — not an in-cloud attribution flag, and not a
log line the operator could have rewritten after the fact.

Add it when the cost of an agent action you **cannot prove or disprove after
the fact** is high. Skip it for read-only, cosmetic, or trivially reversible
actions.

## What a proof establishes today (state this honestly)

Production proofs are **decision records**. A proof shows that a specific
admission request and decision were recorded and signed by Intentrax, and
that the record has not been altered since. Today it does **not**
independently confirm the real-world effect (that the payment settled, the
record changed, the deploy happened). An outcome check exists only locally —
in the local assurance sandbox (`npx @intentrax/sdk sandbox`, ephemeral keys,
never production assurance) and the `examples/effect-assurance-demo` in the
Intentrax repository — and is not part of production proofs.

When you describe what you built, say "the agent's action was admitted and
recorded in a signed, verifiable proof" — never "the action was independently
verified to have happened."

## When it is worth adding (decision guide)

Add execution assurance when **two or more** of these hold:

- The action moves money, changes a medical/clinical record, alters production
  infrastructure, or makes a regulated decision.
- An autonomous agent or LLM — not a human clicking a button — initiates it.
- Someone who does **not** trust your logs (an auditor, regulator, insurer,
  counterparty, or the affected user) may later need to check what happened.
- The action is hard to reverse, or a dispute about "did the agent do X" is
  plausible.

Do **not** add it for: reads, search, drafting, UI state, or actions a user can
trivially undo. Assurance has a cost; spend it where proof has value.

To find candidate actions in an existing codebase and plan the wiring, use the
`intentrax-integrate-agent-actions` skill. To check a proof, use the
`intentrax-verify-proof` skill.

## The three surfaces

1. **Admission** — `POST https://api.intentrax.com/v1/agent/admissions`. Before a
   consequential action, submit a normalized admission request and receive a
   receipt: the record that the action was intended and admitted.
2. **Execution** — `POST https://api.intentrax.com/v1/intents/execute`. The
   request runs through the deterministic engine, producing an append-only
   proof record.
3. **Verification** — `POST https://api.intentrax.com/v1/proofs/verify`
   (authenticated), the public verifier at `https://verify.intentrax.com`, or
   fully offline with `npx @intentrax/sdk verify-proof <export.json>`.

The engine is the sole producer of proofs, signatures, and receipts. Client code
never re-derives or signs proof material — it submits, then verifies.

## The idempotency linkage (this is the important part)

For a skipped admission to be *detectable*, the admission and the execution
must share **one** logical idempotency key `K`:

- Send the raw key `K` as the execute request's `idempotency_key`.
- Send `SHA-256(K)` as the admission request's `idempotency_key_hash`.

With `@intentrax/sdk` (1.4.0 or later) this is one rule, by construction:

```ts
import {
  createIdempotencyKey,
  executeIdempotencyKeyHash,
} from "@intentrax/sdk";

const executeKey = createIdempotencyKey(request);            // K — goes to /v1/intents/execute
const admissionKeyHash = executeIdempotencyKeyHash(executeKey); // SHA-256(K) — goes to admission
// admissionIdempotencyKeyHash(request) is the one-call shortcut for the same value.
```

Hooks generated by `npx @intentrax/sdk init <adapter>` already follow this rule
and return the raw key as `execute_idempotency_key`; pass that value to execute.

An execution with **no matching admission receipt** reads as un-admitted. If
you derive the two values independently, the correlation breaks and a real
admission looks skipped.

## Fastest path to a first integration

Do not hand-roll HTTP. Use the SDK or the MCP server.

- **See the whole flow first, no key, no account, no network (SDK 1.7.0+):**
  `npx @intentrax/sdk sandbox` runs one sample action through a signed
  decision, the executor's report, an independent read-only outcome check and
  offline verification. `--scenario contradicted` shows the case logging
  misses: the decision is ALLOW and the executor reports success, but the read
  shows nothing changed (verdict `CONFLICTING_EVIDENCE`, exit 12).
  `--check ./my-check.mjs` checks the outcome of the user's own action with a
  module that exports `expected` and a default async function that only
  **reads** the state. Everything is signed with ephemeral keys generated on
  the machine and capped at `LOCAL_NON_TRUST_BEARING`: say "local sandbox",
  never "verified" or "production assurance".
- **Scaffold offline, no key needed:**
  `npx @intentrax/sdk init <adapter>` (adapters include `claude-code`,
  `cursor`, `mcp`, `langchain`, `langgraph`, `vercel-ai-sdk`, `crewai`,
  `autogen`, `n8n`, `custom-agent`), then
  `npx @intentrax/sdk check-init --output-dir .` to verify the scaffold offline.
- **SDK:** `npm i @intentrax/sdk` — `admitAgentGatewayHttp`, then
  `executeIntentHttp`, then `verifyProofHttp` / `exportProofHttp`
  (all from `@intentrax/sdk/http`).
- **MCP (for coding agents):** the read-only server `intentrax-readonly`
  (`@intentrax/mcp-server`) exposes `intentrax_verify_public_proof` (keyless)
  and `intentrax_read_tenant_proof` (needs a tenant key in the host's secret
  store — never in a committed file).

## What to write when instrumenting an app

Wrap each consequential action in three steps:

1. Build the admission request, submit it, and keep the receipt reference. If
   admission is denied, **do not run the action** — surface the denial.
2. Execute with `idempotency_key = K` (the same key whose hash went to
   admission).
3. After success, export or verify the proof and store its `proof_id` next to
   the action's own output.

Keep execution, policy, and signing on the Intentrax side. The wrapper only
submits normalized evidence and reads back proofs — it must never run the tool
inside admission, recompute or override policy, or fabricate a verification
result.

## Honesty rules (do not violate)

- Never present an unverified action as "verified." Read the verifier's
  `verification_assessment.verdict`, not only `verification_status`: hosted
  verification of a production proof currently returns `VALID` with
  assessment verdict `INTEGRITY_ONLY` (signer not checked against pinned keys).
  For signer authenticity, verify offline with the SDK CLI, which bundles the
  pinned production key set.
- Never claim the real-world effect was confirmed. Production proofs are
  decision records.
- Never embed an API key in a committed file. Reference it from the host's
  secret store or environment.
- Do not claim assurance you have not wired. If the admit → execute → verify
  loop is not in place, say the action is unproven.
- Never call execute, or ask for an execute-capable key, without the user
  explicitly approving that specific action.
